# ТЗ: многосерверная MCP-оркестрация и универсальный scheduler runtime

## 1. Цель изменений

Доработать проект так, чтобы агент мог работать не с одним MCP-сервером, а с произвольным количеством MCP-сервисов через единый слой оркестрации, а также уметь сохранять и исполнять по расписанию многошаговые маршруты вызова инструментов без участия LLM во время планового запуска.

Итоговый сценарий:

- пользователь общается только через существующий UI;
- агент получает от оркестратора единый список инструментов всех зарегистрированных MCP-сервисов;
- LLM выбирает нужные инструменты по namespaced-именам;
- вызовы идут через MCP-оркестратор, который сам знает, в какой сервис маршрутизировать запрос;
- при создании отложенной задачи LLM сначала формирует последовательность шагов и параметры запуска;
- MCP управления scheduler сохраняет задачу;
- отдельный scheduler runtime по расписанию исполняет сохраненный маршрут без участия LLM;
- ошибки пробрасываются вверх по цепочке до UI и логируются на всех уровнях.

## 2. Целевое архитектурное разбиение

Каждый сервис должен лежать в своей отдельной папке со своим кодом, настройками хранения и логами, чтобы в будущем его можно было вынести на отдельный инстанс.

Планируемые сервисы:

1. `core/mcp_orchestrator`
   Единый MCP-сервис-оркестратор.

2. `core/telegram_mcp`
   Отдельный MCP-сервис, который умеет только работать с Telegram API.

3. `core/gismeteo_mcp`
   Отдельный MCP-сервис, который умеет только получать актуальный прогноз со страницы Gismeteo через локальные вспомогательные методы парсинга HTML.

4. `core/scheduler_service`
   Отдельный runtime-сервис, исполняющий сохраненные задачи по расписанию.

5. `core/scheduler_mcp`
   Отдельный MCP-сервис управления scheduler runtime, задачами и памятью задач.

## 3. Принципы архитектуры

### 3.1. Общие принципы

- UI не меняется по составу виджетов.
- Пользователь работает только через текущий чат.
- Агент не должен напрямую знать о конкретных MCP-серверах, кроме работы с единым оркестратором.
- Scheduler runtime не должен иметь в коде предметных знаний о Telegram, Gismeteo или иных сервисах.
- Scheduler runtime должен исполнять универсальный сохраненный маршрут шагов.
- Все межсервисные взаимодействия должны логироваться полностью.
- Все ошибки должны пробрасываться вверх без потери контекста.

### 3.2. Именование инструментов

Для LLM инструменты должны предоставляться как плоский список namespaced-инструментов:

- `telegram.resolve_chat_id`
- `telegram.send_message`
- `gismeteo.get_current_weather`
- `scheduler.create_task`
- `scheduler.list_tasks`
- `scheduler.delete_task`
- `scheduler.get_task`
- `scheduler.get_task_memory`

Требования:

- имя инструмента должно содержать имя сервиса;
- описание инструмента должно явно содержать, из какого MCP-сервиса он получен;
- оркестратор внутри хранит явный реестр `service -> tools -> client/config`;
- маршрутизация не должна строиться на эвристиках по тексту, только на реестре.

## 4. MCP-оркестратор

### 4.1. Назначение

Оркестратор является единственной MCP-точкой, с которой взаимодействует агент.

### 4.2. Обязанности

- хранить реестр подключенных MCP-сервисов;
- уметь получать список инструментов по всем сервисам;
- уметь получать список инструментов конкретного сервиса;
- отдавать агенту объединенный плоский список инструментов;
- маршрутизировать `call_tool` в нужный MCP-сервис;
- нормализовать ответы;
- логировать полный вход, маршрут и полный выход;
- логировать ошибки маршрутизации и ошибки целевого сервиса.

### 4.3. Поведение `list_tools`

Оркестратор должен:

- обойти зарегистрированные сервисы;
- запросить у каждого `list_tools`;
- преобразовать имена инструментов в namespaced-формат;
- дополнить описание указанием исходного MCP-сервиса;
- вернуть объединенный список.

### 4.4. Поведение `call_tool`

Оркестратор должен:

- принять namespaced-имя инструмента;
- определить целевой MCP-сервис через внутренний реестр;
- передать вызов в нужный сервис;
- вернуть результат без потери структуры;
- при ошибке вернуть структурированную ошибку.

## 5. MCP-сервис Telegram

### 5.1. Назначение

Сервис работает только с Telegram API.

### 5.2. Поддерживаемые инструменты первой версии

- `telegram.resolve_chat_id`
  По логину ищет `chat_id` через Telegram API.

- `telegram.send_message`
  Отправляет сообщение по `chat_id`.

### 5.3. Хранение

Память соответствий `telegram_username -> chat_id` хранится внутри Telegram MCP.

### 5.4. Ограничения

- логика scheduler не должна встраиваться в Telegram MCP;
- Telegram MCP ничего не знает о расписании;
- Telegram MCP только предоставляет инструменты доступа к Telegram API и хранит свои привязки.

## 6. MCP-сервис Gismeteo

### 6.1. Назначение

Сервис работает только на получение актуального прогноза.

### 6.2. Источник данных

Источник фиксированный для первой версии:

- `https://www.gismeteo.ru/weather-tver-4327/`

### 6.3. Поддерживаемые инструменты первой версии

- `gismeteo.get_current_weather`

Требования:

- сам MCP-инструмент вызывает локальные вспомогательные методы;
- вспомогательные методы ходят на HTML-страницу;
- вспомогательные методы парсят HTML;
- результат возвращается как структурированные данные;
- никаких внешних API-ключей и API SDK не использовать.

### 6.4. Ограничения

- MCP Gismeteo не хранит расписания;
- MCP Gismeteo не отправляет сообщения;
- в `list_tools` для первой версии фактически должен быть только один бизнес-инструмент получения прогноза.

## 7. MCP-сервис управления scheduler

### 7.1. Назначение

Этот MCP-сервис управляет scheduler runtime, его задачами и памятью задач.

### 7.2. Обязанности

- создавать задачу;
- удалять задачу;
- получать задачу;
- выводить список задач;
- выводить маршрут задачи;
- выводить память задачи;
- при необходимости отдавать состояние последнего запуска/последней ошибки;
- сохранять конфигурацию маршрута, шаблоны и execution memory на уровне задачи.

### 7.3. Важное разделение ответственности

- MCP управления scheduler сохраняет и читает конфигурацию задач;
- scheduler runtime только исполняет сохраненные задачи;
- runtime не должен зависеть от предметной терминологии конкретных сервисов.

## 8. Scheduler runtime

### 8.1. Назначение

Отдельный сервис, который по расписанию исполняет сохраненные задачи.

### 8.2. Основное поведение

При срабатывании задачи runtime должен:

1. загрузить конфигурацию задачи;
2. прочитать линейный маршрут шагов;
3. выполнять шаги по порядку;
4. сохранять результат каждого успешного шага в execution memory;
5. подставлять сохраненные значения в `arguments_template` следующих шагов;
6. при ошибке немедленно останавливать выполнение текущего запуска;
7. сохранять ошибку в состояние задачи;
8. логировать весь прогон;
9. не обращаться к LLM.

### 8.3. Формат маршрута

Для первой версии берется линейный маршрут шагов с памятью выполнения.

Пример целевой структуры:

```json
{
  "task_id": "task-123",
  "schedule": {
    "every": 1,
    "unit": "minutes"
  },
  "steps": [
    {
      "tool": "telegram.resolve_chat_id",
      "arguments": {
        "username": "some_login"
      },
      "save_result_as": "telegram_binding"
    },
    {
      "tool": "gismeteo.get_current_weather",
      "arguments": {},
      "save_result_as": "weather"
    },
    {
      "tool": "telegram.send_message",
      "arguments_template": {
        "chat_id": "{{telegram_binding.chat_id}}",
        "text": "Сейчас в Твери {{weather.summary}}"
      }
    }
  ]
}
```

### 8.4. Требования к маршруту

- шаги выполняются строго последовательно;
- у шага может быть `arguments` или `arguments_template`;
- результат шага может быть сохранен по ключу `save_result_as`;
- шаблоны должны подставляться из execution memory текущего запуска;
- для первой версии отдельный `transform`-шаг не нужен;
- текст для Telegram хранится как шаблон прямо в задаче.

## 9. Создание задачи через LLM

### 9.1. Поведение

Перед сохранением задачи агент может пройти многошаговый диалог с LLM.

LLM должна иметь возможность:

- увидеть список доступных namespaced-инструментов;
- запросить нужные инструменты у нужных сервисов;
- получить результаты;
- сформировать итоговую последовательность шагов с параметрами;
- вызвать MCP scheduler для сохранения задачи.

### 9.2. Завершение флоу

Флоу считается завершенным, когда:

- либо LLM вернула финальный ответ пользователю;
- либо задача успешно сохранена и агент сообщил результат;
- либо произошла ошибка, которая дошла до UI.

Лимит числа итераций инструментов не должен быть искусственно зафиксирован на малом значении. Требуется подготовить код к потенциально длинному циклу вызовов. Если сохраняется защитный лимит, он должен быть вынесен в конфиг и иметь безопасное, но достаточно большое значение.

## 10. Ошибки и проброс ошибок

### 10.1. Общий принцип

Любая ошибка сервиса должна возвращаться как структурированная ошибка вызывающему уровню и подниматься вверх до UI.

Цепочка проброса:

- целевой MCP-сервис;
- MCP-оркестратор;
- агент;
- UI.

### 10.2. Требования

- ошибка не должна терять исходное сообщение;
- ошибка должна содержать информацию о сервисе и инструменте;
- scheduler runtime должен сохранять ошибку запуска в состояние задачи;
- UI должен показать ошибку в текущем чате/выводе и в существующих логах/метриках без добавления новых UI-элементов.

## 11. Логирование

### 11.1. Общие требования

- каждый сервис логирует в свой отдельный лог;
- формат логов должен быть читаемым;
- JSON должен записываться в pretty-формате;
- в логе должны быть входные параметры, выходные данные, ошибки и маршрут;
- должно быть возможно сопоставить один межсервисный вызов по trace/request id.

### 11.2. Что логируем

На каждом уровне логируется:

1. входящий запрос;
2. нормализованные аргументы;
3. целевой сервис и инструмент;
4. полный ответ;
5. полная ошибка;
6. время выполнения;
7. идентификатор запроса/трассы.

### 11.3. Распределение по сервисам

- у оркестратора должен быть лог факта маршрутизации;
- у целевого сервиса должен быть лог получения вызова и результата;
- при межсервисном вызове в обоих логах должна сохраняться полная переданная структура данных.

## 12. Изменения в существующем проекте

### 12.1. Агент

Нужно изменить слой интеграции MCP в агенте так, чтобы:

- агент работал с оркестратором вместо одиночного MCP-клиента;
- в контекст LLM передавался объединенный namespaced-список инструментов;
- ответы и ошибки оркестратора корректно попадали в историю tool-вызовов;
- информация о маршрутизации и tool events сохранялась в метриках и логах.

### 12.2. MCP-клиент

Текущий клиент, рассчитанный на один сервер, должен быть либо:

- расширен до работы с оркестратором как единой точкой входа;
- либо заменен отдельным клиентом оркестратора.

Внутренний прямой обход множества MCP-сервисов из агента не является целевой моделью.

### 12.3. UI

Новые UI-элементы не добавляются.

Допустимые изменения:

- корректный вывод ошибок в существующий вывод чата;
- корректная запись ошибок и статусов в существующие метрики/логи;
- при необходимости отображение дополнительной текстовой информации в уже существующих областях.

## 13. Минимальный набор пользовательских сценариев для проверки

### 13.1. Разовый инструментальный сценарий

Пользователь просит получить актуальный прогноз.

Ожидаемо:

- LLM выбирает `gismeteo.get_current_weather`;
- оркестратор маршрутизирует вызов;
- агент получает результат и отвечает пользователю.

### 13.2. Сценарий создания задачи по расписанию

Пользователь просит отправлять актуальный прогноз в Telegram каждую минуту.

Ожидаемо:

- LLM получает список всех инструментов;
- LLM определяет необходимые шаги;
- при необходимости вызывает `telegram.resolve_chat_id`;
- вызывает `scheduler.create_task` с маршрутом и шаблоном;
- задача сохраняется;
- агент сообщает пользователю результат.

### 13.3. Сценарий исполнения scheduler runtime

После наступления времени запуска:

- runtime читает задачу;
- идет по маршруту шагов;
- вызывает нужные инструменты через оркестратор;
- получает прогноз;
- отправляет сообщение;
- логирует каждый шаг.

### 13.4. Сценарий ошибки

Любая ошибка одного из шагов должна:

- быть зафиксирована в логе сервиса;
- быть зафиксирована в логе оркестратора;
- быть зафиксирована в состоянии задачи, если ошибка возникла в scheduler runtime;
- дойти до UI, если ошибка произошла в интерактивном пользовательском флоу.

## 14. Критерии готовности

Изменения считаются завершенными, если:

1. агент получает инструменты через единый MCP-оркестратор;
2. система поддерживает добавление произвольного количества MCP-сервисов через реестр;
3. Telegram MCP и Gismeteo MCP вынесены в отдельные сервисные папки;
4. scheduler runtime отделен от MCP управления scheduler;
5. scheduler умеет исполнять линейный маршрут шагов с execution memory;
6. ошибки пробрасываются вверх до UI;
7. на каждом уровне есть подробные отдельные логи;
8. пользовательский сценарий с погодой и Telegram работает через существующий UI;
9. UI не требует новых элементов;
10. кодовая структура позволяет в будущем вынести сервисы на разные инстансы.

## 15. Ограничения первой версии

- источник погоды фиксирован страницей Gismeteo по Твери;
- отдельные ветвления в маршрутах не реализуются;
- отдельный шаг трансформации данных не реализуется;
- шаблонизация ограничивается подстановкой значений из execution memory;
- пользователь работает только через текущий UI.
