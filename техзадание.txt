Техническое задание
Проект: AI Challenge
Дата: 2026-03-04
Тема: День 12. Персонализация ассистента

1. Цель
Реализовать персонализацию ассистента через глобальные пользовательские профили, хранящиеся на стороне сервера, с управлением из UI и автоматическим учетом профиля при генерации ответа (по состоянию тумблера).

2. Функциональные требования
2.1. UI (вкладка Metrics & Memory)
- Разделить вкладку на 2 части через горизонтальный сплиттер.
- Левая часть: текущие блоки Metrics и Memory (сохранить существующую логику).
- Правая часть: новый блок управления профилями пользователя.

2.2. Блок профилей (правая часть)
- Выпадающий список профилей с первым значением по умолчанию: "Без профиля".
- Поле ввода "Описание профиля" (одно текстовое поле).
- Подсказка в UI: в описание можно включать стиль ответа, формат ответа, ограничения.
- Кнопка сохранения профиля (создание/обновление на сервере).
- Кнопка удаления выбранного профиля (без подтверждающего диалога).
- Переименование профиля не требуется.

2.3. Логика выбора профиля и тумблера
- Тумблер "Использовать профиль" является глобальным для клиента.
- Пока выбран "Без профиля", тумблер нельзя включить (disabled).
- При выборе "Без профиля" тумблер автоматически выключается.
- При выборе профиля из списка клиент автоматически запрашивает описание с сервера и заполняет поле.

2.4. Поведение при запросе к агенту
- Клиент не передает профиль целиком в каждом запросе.
- Клиент передает только состояние тумблера (использовать профиль: true/false).
- Сервер сам определяет активный профиль и, если флаг true, добавляет профиль в системный контекст запроса к LLM.

3. Требования к хранению данных
- Профили глобальные, не привязаны к сессиям и веткам.
- Хранить профили в отдельном серверном файле (например: core/agent/profiles.json).
- Формат хранения должен поддерживать:
  - список профилей (имя, описание, даты создания/обновления),
  - активный профиль (или пустое значение),
  - глобальный флаг использования профиля (по необходимости можно хранить на сервере для диагностики, но источник факта включения - запрос клиента).
- При старте приложения активный профиль по умолчанию не выбран ("Без профиля").

4. Серверный API (JSONL protocol)
Добавить действия (actions) в LLMAgentServer/AgentClient:
- list_profiles: вернуть список профилей.
- get_profile: вернуть описание выбранного профиля.
- save_profile: создать/обновить профиль.
- delete_profile: удалить профиль.
- set_active_profile: установить активный профиль на сервере.
- get_profile_state: вернуть текущее состояние (active_profile, available_profiles).

Изменить stream_chat:
- Принимать флаг use_profile (bool).
- Если use_profile=true и активный профиль установлен:
  - формировать system-блок профиля,
  - объединять с существующим system_text (memory/facts/summary) без потери текущей логики.

5. Формирование контекста профиля
- Профиль должен быть добавлен как отдельный системный блок перед запросом в LLM.
- Рекомендуемый формат блока:
  USER PROFILE:
  - name: <profile_name>
  - description: <profile_description>
  Follow this profile automatically when generating the answer.
- Если profile отключен или не выбран, блок профиля в контекст не добавлять.

6. Логирование
6.1. Серверные логи
В логи запроса (SERVER_API_REQUEST и/или done-ответ) добавить поля:
- use_profile
- active_profile
- profile_description_len
- profile_applied (true/false)

6.2. Клиентские метрики
В строку metrics на каждый запрос добавить:
- use_profile=true/false
- active_profile=<имя или "Без профиля">
- description_len=<число>

  - Использовать профильные контролы из MetricsMemoryTab.
  - Добавить вызовы новых API клиента.
  - Передавать в stream_chat только use_profile.
  - Расширить строку metrics профильными полями.
- core/agent/agent_client.py
  - Добавить RPC-методы для профилей.
  - Расширить stream_chat параметром use_profile.
- core/agent/agent_server.py
  - Добавить handlers для profile actions.
  - Добавить загрузку/сохранение файла профилей.
  - Интегрировать профиль в system_text при use_profile=true.
  - Расширить логирование профильными полями.
- core/agent/
  - Добавить модуль/класс хранилища профилей (например profile_store.py) или встроить в существующий storage-слой.

  - Новый файл хранения профилей.

8. Нефункциональные требования
- Не ломать существующие стратегии контекста (sliding/facts/summary/branching).
- Не ломать текущую работу sessions/branches/checkpoints/memory layers.
- Ошибки profile API должны логироваться и корректно показываться в UI.

9. Критерии приемки
- На вкладке Metrics & Memory есть две части (splitter), профильный блок справа.
- Есть режим "Без профиля" по умолчанию.
- Тумблер нельзя включить, пока не выбран профиль.
- Выбор "Без профиля" выключает тумблер автоматически.
- Сохранение профиля создает/обновляет профиль на сервере.
- Удаление профиля удаляет его сразу, без подтверждения.
- При выборе профиля описание автоматически подгружается с сервера.
- В stream_chat уходит только use_profile, а не весь текст профиля.
- При use_profile=true сервер добавляет активный профиль в контекст LLM.
- В серверных логах видны поля use_profile/active_profile/profile_description_len/profile_applied.
- В клиентских Metrics видны use_profile/active_profile/description_len.

10. Вне scope текущей задачи
- Переименование профиля.
- Привязка профиля к сессиям/веткам.
- Пресеты профилей.
